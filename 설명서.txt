■ 0. 이 프로젝트가 하는 일 (한 줄)
================================================================================

  SI 개발 계약서(기획서) PDF 한 장을 contract/ 에 넣으면 → 기능정의 → 페이지맵 →
  실제 동작하는 HTML 화면 시안 → 고객 공유용 기획문서 까지를
  사람 개입 거의 없이(autopilot) 자동으로 뽑아내는 Claude Code 워크플로우 키트.

  산출물은 전부 repo 루트에 flat 하게 생성된다 (01_FEAT.md / 02_PAGE.md / pages/ / docs/).
  한 번에 한 기획서만 다룬다 — 여러 고객사 폴더 관리는 하지 않는다.

  ※ 고객사가 로그인해서 시안을 열람하고 페이지별 코멘트를 다는 "포털"은
    별도 repo로 개발한다. 이 repo는 콘텐츠 공장 — 기획자는 여기서 결과물만 확인.


■ 1. 폴더·파일 구성 (무엇이 무엇을 하는가)
================================================================================

  [규격·지침 — 사람이 읽는 source of truth]
   README.md      프로젝트 개요 + 빠른 시작 (공개 repo 첫 화면)
   CLAUDE.md      각 단계 산출물의 형식·디자인 규칙 (가장 권위 있는 문서)
   DESIGN.md      Notion 톤 디자인 토큰 (색·라운드·그림자·타이포) + 모바일 디바이스 프레임 스펙
   AGENT.md       main 오케스트레이터의 단계별 실행 룰 + 마커 프로토콜

  [자동화 키트 — Claude가 실행]
   .claude/commands/build.md         /build 진입점 (전 파이프라인 자동 실행)
   .claude/agents/*.md               7개 전담 sub-agent 정의 (각자 모델 지정)
   .claude/hooks/*.ps1               3개 PowerShell 훅 (상태 추적·강제 진행)
   .claude/settings.json             훅 등록 + 출력/사고 토큰 한도
   .claude/settings.local.json       권한(allow/deny) 정책

  [입력·산출물 — repo 루트, flat]
   contract/*.pdf                    기획서(계약서) 원본 — 입력 트레이 겸 보관
   01_FEAT.md                        기능 카탈로그 표 (1단계)
   02_PAGE.md                        페이지 맵 표+트리 (2단계) — "파일" 컬럼 필수
   pages/index.html                  페이지 허브
   pages/assets/css/common.css       공통 스타일
   pages/user/*.html                 사용자(모바일) 시안
   pages/admin/*.html                관리자(PC) 시안
   docs/index.html                   고객 공유용 기획 문서 (마무리)

  현재 repo에는 예시 1건(가상의 코워킹 스페이스 "모두라운지" 회의실·좌석 예약 서비스,
  contract/sample-contract.pdf)의 산출물이 들어 있다. 실제 고객사 정보는 없다 —
  파이프라인이 어떤 결과를 내는지 보여주는 데모용이며, 자기 기획서로 바꿔 /build 하면
  전부 새로 덮어써진다.


■ 2. 사용법
================================================================================

  ▶ 새 기획서 1건 처리 (가장 일반적)
     1) contract/ 에 기획서 PDF 를 넣는다. (이전 PDF는 지우거나 그대로 둬도 됨 —
        여러 개면 가장 최근 파일이 대상)
     2) 채팅에 /build 입력 (또는 "시작" / "ㄱㄱ" / "go" 등 진행신호).
     3) 끝날 때까지 기다린다. 중간에 스코프 질문은 하지 않는다(보수적으로 포함).
     4) 완료되면 main이 기능/페이지/파일 수 + 해석 포인트를 요약 보고한다.

  ▶ 재빌드 (계약서는 그대로, 산출물만 다시)
       그냥 /build — 항상 처음부터 다시 실행이다.
       (이전 산출물 중 01_FEAT/02_PAGE/pages의 user·admin·index.html 을 리셋하고 시작.
        common.css 와 docs/index.html 은 새로 덮어써진다.)

  ▶ 중단된 파이프라인 이어가기
       /build 를 다시 치지 말 것 (처음부터 다시 함).
       그냥 채팅으로 "계속" 진행신호만 주면 Stop 훅이 디스크 상태(어느 파일·마커가
       비었나)로 남은 단계를 알아서 이어간다.

  ▶ 중단하고 싶을 때
       "중단"이라고 말하면 main이 .claude/_autopilot 마커를 제거하고 멈춘다.
       (수동으로 멈추려면: Remove-Item ".claude/_autopilot" )

  ▶ 시안 미리보기
       VS Code Live Server(포트 5501)로 pages/index.html (시안 허브) 또는
       docs/index.html (고객 문서)를 연다. pages/ 폴더 구조를 유지한 채 서빙해야
       페이지 간 상대경로 링크가 동작한다.

  ▶ 이 키트를 새 repo로 복사할 때 (재사용)
       CLAUDE.md + DESIGN.md + AGENT.md + .claude/ 전체 + 빈 contract/ 만 가져간다.
       기존 산출물(01_FEAT.md / 02_PAGE.md / pages/ / docs/)은 복사하지 않는다.


■ 3. 동작 원리 요약 (자세한 흐름은 동작방식.txt)
================================================================================

  핵심은 "마커 파일 상태기계 + 3개의 훅"이다.

  (1) main 은 오케스트레이터다. 직접 산출물을 만들지 않고 전담 sub-agent 에 위임한다.
  (2) 각 단계가 끝나면 별도 컨텍스트의 reviewer(opus) 가 검토한다.
      main 은 자기 산출물을 스스로 "통과"시키지 못한다 (자가-합리화 차단).
  (3) reviewer 통과 + 권고 반영이 끝나야 main 이 .claude/_reviewed_stageN 마커를 만든다.
  (4) Stop 훅은 매 턴 끝에서 "어느 단계가 비었나"를 디스크에서 재계산해 다음 단계를
      main 에게 강제 주입한다. 다 차기 전엔 턴 종료를 막는다 → 끝까지 굴러간다.
  (5) PostToolUse 훅은 상위 산출물(01_FEAT/02_PAGE)이 바뀌면 하위 단계 검토 마커를
      무효화해, 위가 바뀌면 아래를 다시 검토하게 만든다.
  (6) ★ 3단계 완료 판정은 "파일 개수"가 아니라 "파일 내용"이다:
      02_PAGE.md "파일" 컬럼의 모든 페이지가 존재 + 400B 이상 + common.css import
      여야 통과. 빈 <html></html> 스텁이나 표에 없는 고아 파일로는 못 넘어간다.
  (7) 무한루프 방지: 같은 단계에서 연속 스톨이 상한(단발 8 / 양산·검토 20)에
      도달하면 안전밸브가 autopilot 을 강제 해제하고 상황을 보고한다.

  → 사람이 단계를 지시하지 않아도, "디스크의 상태"가 곧 진행 상태이고
    훅이 그걸 읽어 다음 행동을 정한다. 이게 이 키트가 autopilot으로 도는 원리.


■ 4. "잘 동작할까?" — 종합 판단
================================================================================

  결론: 정상 경로(contract/ PDF 1건 → /build)에서 완주하도록 견고하게 설계돼 있고,
        2026-07 개정에서 "완주는 하는데 내용이 빈" 사고까지 구조적으로 막았다.

   ✓ Stop 훅이 매번 "디스크 상태"에서 다음 단계를 재계산한다.
     → 모델이 한 단계를 깜빡하거나 PostToolUse 주입이 누락돼도, Stop 훅이
       파일 존재·내용으로 빠진 단계를 다시 지시한다. (상태가 대화기억이 아니라
       파일에 있으므로 컨텍스트가 잘려도 복구된다.)
   ✓ 검토 게이트가 구조적으로 강제된다.
     → 마커는 reviewer 통과 후에만 생기고, sub-agent는 reviewer를 못 부른다.
   ✓ 완료 게이트가 내용을 검사한다.
     → 과거 실제 사고: exemplar 포함 5장이 빈 <html></html> 스텁인 채 "개수"만
       채워져 delivered 로 완주한 적이 있다. 지금은 파일별 내용 검사(빈 스텁·
       common.css import)와 P#↔파일 1:1 대조(파일 컬럼·고아 감지)가 이를 차단한다.

■ 6. 점검·디버깅 치트시트
================================================================================

  현재 진행상태 보기 (어느 마커가 차 있나):
     Get-ChildItem .claude\_* -Force

  연속 스톨 횟수(안전밸브까지 여유) + 현재 막혀있는 단계:
     Get-Content .claude\_autopilot_count   # 상한(단발 8/양산·검토 20)에 가까우면 곧 강제 해제
     Get-Content .claude\_autopilot_stage   # 지금 어느 단계에서 막혀있나 (feat/review1/build-.../docs 등)
     # 단계가 진행되면 _count는 1로 리셋되므로, 상한에 가까운데 _stage가 그대로면 진짜 교착

  파이프라인 강제 중단:
     Remove-Item .claude\_autopilot

  특정 단계부터 다시 검토시키기 (예: 2단계부터):
     Remove-Item .claude\_reviewed_stage2,.claude\_reviewed_stage3,.claude\_docs_done

  페이지 정합성 확인 (훅과 동일한 "파일 컬럼" 기준):
     # 02_PAGE.md 파일 컬럼의 기대 파일 목록:
     [regex]::Matches((Get-Content 02_PAGE.md -Raw), '(user|admin)/[A-Za-z0-9_\-]+\.html') | ForEach-Object { $_.Value } | Sort-Object -Unique
     # 실제 파일 + 크기 (400B 미만이면 빈 스텁 = 미완성):
     Get-ChildItem pages\user,pages\admin -Filter *.html | Select-Object Name,Length

  훅이 멈췄을 때: powershell 실행정책/경로 확인
     - settings.json 의 훅은 -ExecutionPolicy Bypass 로 호출되므로 정책 문제는 드묾.
     - .ps1 파일 경로(.claude/hooks/*.ps1)가 repo 루트 기준 상대경로임에 유의
       (Claude Code 는 repo 루트에서 훅을 실행한다).
