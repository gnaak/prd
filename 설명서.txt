================================================================================
 설명서 — 계약서 → HTML 화면정의 자동화 키트
================================================================================
 작성일: 2026-06-30
 범위: 프로젝트 전체 검토 + 사용법 + 동작 설명 + 예상 문제와 대처
 같이 볼 것: 동작방식.txt (흐름도), CLAUDE.md (산출물 규격), AGENT.md (오케스트레이션 룰)
--------------------------------------------------------------------------------


■ 0. 이 프로젝트가 하는 일 (한 줄)
================================================================================

  SI 개발 계약서 PDF 한 장을 넣으면 → 고객사 식별 → 기능정의 → 페이지맵 →
  실제 동작하는 HTML 화면 시안 → 고객 공유용 기획문서 까지를
  사람 개입 거의 없이(autopilot) 자동으로 뽑아내는 Claude Code 워크플로우 키트.

  산출물은 전부 고객사별 폴더 html/clients/{slug}/ 안에 쌓인다.
  이 {slug} 가 나중에 포털/백엔드의 테넌트(Org) 키로 그대로 쓰일 설계.


■ 1. 폴더·파일 구성 (무엇이 무엇을 하는가)
================================================================================

  [규격·지침 — 사람이 읽는 source of truth]
   CLAUDE.md      각 단계 산출물의 형식·디자인 규칙 (가장 권위 있는 문서)
   DESIGN.md      Notion 톤 디자인 토큰 (색·라운드·그림자·타이포)
   AGENT.md       main 오케스트레이터의 단계별 실행 룰 + 마커 프로토콜

  [자동화 키트 — Claude가 실행]
   .claude/commands/build.md         /build 진입점 (전 파이프라인 자동 실행)
   .claude/agents/*.md               8개 전담 sub-agent 정의 (각자 모델 지정)
   .claude/hooks/*.ps1               3개 PowerShell 훅 (상태 추적·강제 진행)
   .claude/settings.json             훅 등록 + 출력/사고 토큰 한도
   .claude/settings.local.json       권한(allow/deny) 정책

  [산출물 — 고객사별]
   html/_inbox/                      새 계약서 PDF를 여기 투입 (입력 트레이)
   html/clients/{slug}/
     client.json                     고객사 신원 메타 (0단계)
     contract/*.pdf                  그 고객사 계약서 원본
     01_FEAT.md                      기능 카탈로그 표 (1단계)
     02_PAGE.md                      페이지 맵 표+트리 (2단계)
     pages/index.html                페이지 허브
     pages/assets/css/common.css     공통 스타일 (고객사마다 자기 사본)
     pages/user/*.html               사용자(모바일) 시안
     pages/admin/*.html              관리자(PC) 시안
     docs/index.html                 고객 공유용 기획 문서 (마무리)

  현재 repo에는 예시 고객사 1곳(modulounge / 모두라운지)이 완성(delivered)되어 있다.


■ 2. 사용법
================================================================================

  ▶ 새 계약서 1건 처리 (가장 일반적)
     1) html/_inbox/ 에 계약서 PDF 를 넣는다.
     2) 채팅에 /build 입력 (또는 "시작" / "ㄱㄱ" / "go" 등 진행신호).
     3) 끝날 때까지 기다린다. 중간에 스코프 질문은 하지 않는다(보수적으로 포함).
     4) 완료되면 main이 고객사/페이지/파일 수 + 해석 포인트를 요약 보고한다.

  ▶ 기존 고객사 재빌드 (계약서는 그대로, 산출물만 다시)
       /build {slug}      예) /build modulounge
     → client-init(0단계) 생략, 단계 산출물 리셋 후 1단계부터 다시.

  ▶ 중단된 파이프라인 이어가기
       /build 를 다시 치지 말 것 (처음부터 다시 함).
       그냥 채팅으로 "계속" 진행신호만 주면 Stop 훅이 _current_client 로
       남은 단계를 알아서 이어간다.

  ▶ 중단하고 싶을 때
       "중단"이라고 말하면 main이 .claude/_autopilot 마커를 제거하고 멈춘다.
       (수동으로 멈추려면: Remove-Item ".claude/_autopilot" )

  ▶ 이 키트를 새 repo로 복사할 때 (재사용)
       CLAUDE.md + DESIGN.md + AGENT.md + .claude/ 전체 + 빈 html/_inbox/ 만 가져간다.
       기존 html/clients/* 산출물은 복사하지 않는다.


■ 3. 동작 원리 요약 (자세한 흐름은 동작방식.txt)
================================================================================

  핵심은 "마커 파일 상태기계 + 3개의 훅"이다.

  (1) main 은 오케스트레이터다. 직접 산출물을 만들지 않고 전담 sub-agent 에 위임한다.
  (2) 각 단계가 끝나면 별도 컨텍스트의 reviewer(opus) 가 검토한다.
      main 은 자기 산출물을 스스로 "통과"시키지 못한다 (자가-합리화 차단).
  (3) reviewer 통과 + 권고 반영이 끝나야 main 이 .claude/_reviewed_stageN 마커를 만든다.
  (4) Stop 훅은 매 턴 끝에서 "어느 마커가 비었나"를 보고 다음 단계를 main 에게
      강제 주입한다. 마커가 다 차기 전엔 턴 종료를 막는다 → 끝까지 굴러간다.
  (5) PostToolUse 훅은 상위 산출물(01_FEAT/02_PAGE)이 바뀌면 하위 단계 검토 마커를
      무효화해, 위가 바뀌면 아래를 다시 검토하게 만든다.
  (6) 무한루프 방지: Stop 차단이 20회를 넘으면 안전밸브가 작동해 강제 종료한다.

  → 사람이 단계를 지시하지 않아도, "디스크의 마커 상태"가 곧 진행 상태이고
    훅이 그걸 읽어 다음 행동을 정한다. 이게 이 키트가 autopilot으로 도는 원리.


■ 4. "잘 동작할까?" — 종합 판단
================================================================================

  결론: 정상 경로(새 PDF 1건 → /build)에서는 잘 동작하도록 견고하게 설계돼 있다.
        특히 다음 두 가지가 안정성의 핵심이다.

   ✓ Stop 훅이 매번 "디스크 상태"에서 다음 단계를 재계산한다.
     → 모델이 한 단계를 깜빡하거나 PostToolUse 주입이 누락돼도, Stop 훅이
       파일 존재 여부로 빠진 단계를 다시 지시한다. (상태가 대화기억이 아니라
       파일에 있으므로 컨텍스트가 잘려도 복구된다.)
   ✓ 검토 게이트가 구조적으로 강제된다.
     → 마커는 reviewer 통과 후에만 생기고, sub-agent는 reviewer를 못 부른다.
       "대충 만들고 스스로 OK"가 원천 차단된다.

  실제로 예시 고객사(modulounge)가 14개 페이지맵 → 16개 HTML + docs 까지
  delivered 상태로 완주해 있어, 파이프라인이 끝까지 도는 것은 검증된 셈이다.

  앞서 발견됐던 문제 P1~P7 은 모두 수정·적용 완료(아래 5장). 남은 것은 환경 전제(P8)뿐.


■ 5. 수정 내역 (P1~P7 적용 완료, 2026-06-30)
================================================================================

  ┌─ [P1] ★높음★  새 PDF 이동: git mv → Move-Item ───────────────────────────┐
   문제: 방금 _inbox에 떨어뜨린 새 PDF는 git 미추적 상태라 `git mv`가
         "not under version control"로 실패할 수 있었다.
   수정: build.md / AGENT.md 의 PDF 이동을 `Move-Item` 으로 교체.
         (New-Item -ItemType Directory -Force ...; Move-Item "_inbox/x.pdf" ".../contract/x.pdf")
   확인: 추적/커밋이 필요하면 이동 후 일반 `git add` 로 한다.

  ┌─ [P2] ★중간★  권한 deny 규칙을 위험 경로만 차단하도록 좁힘 ──────────────┐
   문제: deny에 "Remove-Item -Recurse -Force *" 같은 포괄 규칙이 있어
         프로젝트 내부 스코프 삭제(재빌드 리셋)까지 막을 소지가 있었다.
   수정: settings.local.json 의 포괄 규칙을 제거하고, 위험 루트만 타깃팅
         (C:* / /* / ~* / ..* / $env:* + rm -rf 변형). bash deny 철학과 동일.
   확인: html/clients/... 같은 상대경로 재귀삭제는 허용, 재앙적 삭제만 차단.

  ┌─ [P3] ★중간★  Stop 카운터를 "진행도 기반 스톨 카운터"로 교체 ────────────┐
   문제: 옛 카운터는 "한 턴 = +1, 빌드 내내 누적, 상한 20". 페이지가 많거나
         재검토가 길면 정상 진행 중에도 20을 넘겨 중간에 끊길 수 있었다.
   수정: autopilot-gate.ps1 — 단계 태그(_autopilot_stage)를 두고, 단계가 바뀌면
         (=진전) 카운터를 0으로 리셋, 같은 단계가 반복되면(=스톨) +1.
         상한은 12(연속 스톨). 양산은 build-N-of-M 태그가 매 페이지 바뀌므로
         아무리 페이지가 많아도 트립하지 않는다. reviewer 무한 블로커·스코프
         교착처럼 "같은 단계 12턴 연속 진전 없음"일 때만 강제 해제.
   확인: 유닛테스트로 (a)16턴 양산=트립X, (b)동일 review 단계=12에서 트립,
         (c)11턴 막힘 후 진전=1로 리셋 을 검증함.

  ┌─ [P4] ★중간★  Stop 훅이 백본임을 코드·문서에 명시 ───────────────────────┐
   문제: 3단계 완성 자동감지(PostToolUse)가 sub-agent Write에서 안 뜰 수 있다는
         불확실성.
   수정: check-stage.ps1 상단 주석 + AGENT.md 에 "진행 강제 백본 = Stop 훅,
         PostToolUse는 편의 트리거" 를 명문화. Stop 훅은 매 턴 디스크 상태에서
         다음 단계를 재계산하므로 PostToolUse가 빠져도 동일 판정으로 커버.
   확인: 기능 변경 아님 — 설계 의도를 문서/코드에 고정.

  ┌─ [P5] ★낮음★  페이지 수(expected) 계산을 표 행에 고정 ───────────────────┐
   문제: 옛 정규식 \bP\d+\b 는 02_PAGE.md 전체를 훑어, 트리/본문의 P# 언급이나
         오타 "P15"가 expected를 부풀려 양산이 끝나지 않을 수 있었다.
   수정: 두 훅 모두 (?m)^\s*\|\s*(P\d+)\b — "페이지 목록" 표에서 셀 첫 칸이
         P#인 행만 카운트. 트리·본문 언급은 무시.
   확인: modulounge 에서 expected=14 (기존과 동일하되 견고). 양산 무한반복 방지는
         P3 스톨 카운터가 추가 안전망. 단, 페이지=파일 1:1 유지는 여전히 권장.

  ┌─ [P6] ★낮음★  검토 후 페이지 수정 → _reviewed_stage3 무효화 ─────────────┐
   문제: AGENT.md는 "산출물 수정 시 이후 검토 마커 제거"라 했지만, 실제로는
         01_FEAT/02_PAGE 만 처리하고 pages/*.html 수정은 stage3 마커를 안 깼다.
   수정: check-stage.ps1 — _reviewed_stage3 가 이미 있는 상태에서 pages/*.html이
         수정되면 _reviewed_stage3 + _docs_done 제거하고 "linter→reviewer 재검토"
         주입. 양산 중(검토 전)엔 마커가 없으므로 무효화 없이 카운트만 본다.
         AGENT.md 문구도 단계별 정확히 재기술.
   확인: 코드와 문서가 일치. 검토 후 손댄 페이지는 재검토를 거친다.

  ┌─ [P7] ★낮음★  client.json 스키마에 created 정식 편입 ────────────────────┐
   문제: 예시엔 5필드(slug/name/project/contract/status)뿐인데 실제 modulounge엔
         created 가 더 있어 스키마 드리프트.
   수정: CLAUDE.md / client-init.md 의 정식 스키마를 6필드로 명문화
         (created = 빌드 시작일 YYYY-MM-DD). client-init은 호출 프롬프트의 오늘
         날짜로 채우고(없으면 ""), main이 셋업 때 빈 값을 보정. "그 외 키 금지" 명시.
   확인: modulounge client.json 키 = slug,name,project,contract,status,created (정합).

  ┌─ [P8] ★환경★  Windows / 인코딩 / PowerShell 의존성 (상시 전제 — 수정 대상 아님) ┐
   - 훅은 전부 PowerShell(.ps1) + win32 전제. macOS/Linux로 옮기면 훅을 재작성해야 함.
   - 마커/_current_client/_autopilot_stage 는 ascii로 읽고 쓴다(slug·태그가 ascii라 안전).
     slug에 한글이 섞이면 안 된다(client-init이 로마자 음차하므로 정상 경로에선 문제없음).
   - 한글 파일명 PDF(예: "5. 계약서 1부..pdf") 이동 시 따옴표 필수(공백·점 포함).


■ 6. 점검·디버깅 치트시트
================================================================================

  현재 진행상태 보기 (어느 마커가 차 있나):
     Get-ChildItem .claude\_* -Force

  현재 빌드 중 고객사:
     Get-Content .claude\_current_client

  연속 스톨 횟수(안전밸브까지 여유) + 현재 막혀있는 단계:
     Get-Content .claude\_autopilot_count   # 12에 가까우면 곧 강제 해제 (같은 단계 연속 스톨)
     Get-Content .claude\_autopilot_stage   # 지금 어느 단계에서 막혀있나 (feat/review1/build-.../docs 등)
     # 단계가 진행되면 _count는 1로 리셋되므로, 12에 가까운데 _stage가 그대로면 진짜 교착

  파이프라인 강제 중단:
     Remove-Item .claude\_autopilot

  특정 단계부터 다시 검토시키기 (예: 2단계부터):
     Remove-Item .claude\_reviewed_stage2,.claude\_reviewed_stage3,.claude\_docs_done

  페이지 수 정합성 확인 (훅과 동일한 표-행 기준 카운트):
     # 02_PAGE.md "페이지 목록" 표의 P# 행 개수 vs 실제 html 파일 수가 맞는지
     ([regex]::Matches((Get-Content html\clients\{slug}\02_PAGE.md -Raw), '(?m)^\s*\|\s*(P\d+)\b') | ForEach-Object { $_.Groups[1].Value } | Sort-Object -Unique).Count
     Get-ChildItem html\clients\{slug}\pages\user,html\clients\{slug}\pages\admin -Filter *.html

  훅이 멈췄을 때: powershell 실행정책/경로 확인
     - settings.json 의 훅은 -ExecutionPolicy Bypass 로 호출되므로 정책 문제는 드묾.
     - .ps1 파일 경로(.claude/hooks/*.ps1)가 repo 루트 기준 상대경로임에 유의
       (Claude Code 는 repo 루트에서 훅을 실행한다).


■ 7. 변경 시 주의 (키트를 손볼 때)
================================================================================

  - 단계를 추가/삭제하면 3곳을 함께 고쳐야 한다:
      (1) autopilot-gate.ps1 의 판정 트리, (2) check-stage.ps1 의 마커 무효화 규칙,
      (3) AGENT.md/build.md 의 절차 + 마커 표.
    세 곳이 어긋나면 게이트가 영영 안 열리거나 단계를 건너뛴다.
  - 마커 이름을 바꾸면 위 3곳 + CLAUDE.md 의 마커 표까지 전부 동기화.
  - sub-agent의 model frontmatter를 바꿔도 CLAUDE_CODE_SUBAGENT_MODEL 이 설정돼
    있으면 무시된다 — 그 환경변수는 절대 켜지 말 것.
  - reviewer는 read-only여야 한다(수정은 main 몫). tools에 Write를 주지 말 것.
